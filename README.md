# 코멘토 직무부트캠프 — Computer Vision POC


## [1차] 픽셀 단위 이미지 처리 → [`01_image_processing/`](01_image_processing/)

OpenCV로 위성 영상에서 특정 색상 화소를 검출하고, AI 학습용 전처리 파이프라인을
구성했습니다.

- **검출 범위를 측정으로 고쳤습니다.** 과제 예제의 빨강 범위(H 0~10, S≥120)는
  프랑스 Aigues-Mortes 염전을 0.41%밖에 못 잡습니다. 실제 화소를 재니
  H 7~11, **S 96~135** 로, 채도 하한 120에서 절반이 잘려 있었습니다. 범위를
  맞추니 검출량이 **2.15배**가 됐습니다.
- **이상치 임계값을 분포에서 정했습니다.** food101 1,000장의 밝기·면적비 분포를
  그려 왜도에 따라 기준을 골랐습니다. 기존 밝기 임계값 40은 1,000장에서
  **한 장도 걸러내지 못하고 있었습니다.**
- **정답 마스크 없이 검출 품질을 추정했습니다.** 100개 패치를 층화 추출해
  판정하고 윌슨 신뢰구간으로 정밀도 **88.0%** (76.2~94.4%)를 얻었습니다.
  능동학습 표본은 무작위 표본이 0개 찾은 놓침을 5개 찾아냈습니다.
- **증강을 학습 중 실시간으로 옮겼습니다.** PyTorch `Dataset.__getitem__`에서
  매번 난수를 뽑습니다. 사전 저장 대비 **60.8 GB** 절약.

## [2차] 2D → 3D 변환 → [`02_2d_to_3d/`](02_2d_to_3d/)

**달 사진 두 장으로 지형의 높낮이를 복원했습니다.** 착륙 지점을 고르려면 어디가
평평한지 알아야 하는데, 사진에는 색만 있고 높낮이가 없습니다. 같은 곳을 각도를
바꿔 두 번 찍고 두 사진에서 밀린 정도로 거리를 재는 **수렴 스테레오**입니다.
대상은 티코 크레이터, 정답은 LRO LOLA 레이저 고도계로 실제 측정된 고도입니다.

- **고도 오차 중앙값 30 m — 높낮이 차 5,376 m 의 0.56% 입니다.**
  시차 1픽셀이 450 m 를 바꾸는 촬영 조건이므로 한 픽셀보다 작게
  맞춘 셈입니다. 10곳 중 9곳이 82 m 안에 들고, 복원한 점은
  311,550개입니다.
- **1971년에 실제로 찍힌 사진으로도 확인했습니다.** 아폴로 15호 매핑 카메라가
  24초 간격으로 필름에 찍은 두 장을 같은 파이프라인에 넣었습니다. 사진에서 잰
  것만으로 계산한 카메라 고도가 **102.5 km** 로 아카이브 기록 100.9 km 와
  1.6% 안에서 맞고, 복원한 높낮이 차가 **2.74 km** 로 레이저 측정치
  2.72 km 와 1.01 배 안에서 맞습니다. 어느 쪽도 정답 고도를 보고 맞춘
  값이 아닙니다.
- **믿을 수 없는 곳을 정답 없이 걸러 냅니다.** 좌우 일관성 · 광도 잔차 · 정합
  봉우리의 뾰족함을 넣고, 그것이 실제 오차를 예측하는지 희소화 곡선과 AUC 로
  쟀습니다. 크게 틀린 화소를 골라내는 AUC 가 광도 잔차 0.94, 각도 간 편차
  0.97 입니다. 실제로 걸어서 RMSE 가 100 → 72 m 로 줄었습니다.
  재 보기 전에는 몰랐던 것도 나왔습니다 — **국소 대비는 무작위보다 나쁩니다.**
- **파라미터를 영상에서 정합니다.** 대비 하한을 절대값으로 박는 대신 영상의
  잡음에서 유도합니다(잡음 x 2 = 1.42). 블록 크기는 각도 간
  불일치와 재조명 일치도를 합쳐 정답 없이 고릅니다.
- **정밀도와 덮는 범위가 맞바뀌는 것을 측정했습니다.** 두 시선이 벌어진 각을
  10°에서 30°로 키우면 오차가 58 → 28 m 로 줄지만 값이 나온 화소가
  77 → 43% 로 떨어집니다. 각도가 다르면 성공하는 곳도 다르므로,
  네 각도를 합쳐 둘 다 얻었습니다.
- **렌더링이 시차를 밀어내던 버그를 테스트가 잡았습니다.** 처음 오차가 1,245 m 로
  한쪽에 치우쳐 있었습니다. 점을 화소에 던져 그릴 때의 반올림 오차가 경사
  방향으로 쏠렸고, 두 촬영 지점이 반대로 기울어 있어 좌우가 반대로 쏠린
  것이었습니다. 화소마다 광선을 쏘는 방식으로 바꿔 시차 치우침이
  **2.6 → 0.1 픽셀** 이 됐습니다.
- **Unit Test 79개.** 평지를 수직으로 보면 깊이가 촬영 고도와 같아야 한다,
  베이스라인이 `2·H·tan(수렴각/2)` 를 만족해야 한다처럼 **손으로 답을 낼 수
  있는 조건**으로 숫자까지 대조했습니다. 찾은 버그는 전부 회귀 테스트로
  고정했습니다.
- **남은 것.** 실제 사진 결과를 지도 좌표에 놓아 화소마다 채점하는 일과, 남긴
  값이 얼마나 정확한지를 말하는 일입니다. 크게 틀린 화소는 골라내지만 오차의
  크기까지는 못 맞힙니다.

## [3차] 위성사진 선박 객체탐지 → [`03_ship_detection/`](03_ship_detection/)

**10 m 해상도 위성사진에서 5 픽셀짜리 선박을 찾았습니다.** Sentinel-2 는 무료로
전 지구를 5일마다 찍지만 배 한 척이 서너 화소밖에 안 됩니다. 핀란드 연안 공개
주석에 AWS 공개 COG 를 맞춰 학습셋을 만들고, DOTA 항공영상 사전학습 모델을
파인튜닝했습니다. 평가는 학습에 안 쓴 해역에서만 했습니다.

- **못 본 해역에서 test mAP50 0.9014 입니다.** train·val·test 를 지역 단위로
  갈랐습니다(34VEM 외 / 34VER / 34WFT). 같은 해역이 섞이면 수치가 부풀려지기
  때문입니다. 대조군 넷으로 기여도를 갈라 보니 **증강 +13.2%p · 사전학습
  +2.8%p · 모델 크기 +2.4%p** 로, 가장 크게 기여한 것은 구조가 아니라
  증강이었습니다.
- **mAP50-95 0.459 는 모델의 성능이 아니라 지표의 산물이었습니다.** 같은 모델을
  점 기준으로 재면 **AP 0.911 · 재현율 0.992 · 중심 오차 0.46 px(약 5 m)**
  입니다. 5 픽셀짜리 물체에 IoU 0.75 를 요구하는 것은 부분 픽셀 정확도를
  요구하는 것과 같습니다. 같은 10 m 급인 xView3-SAR 도 박스를 버리고 점 기반
  F1 을 씁니다.
- **왜 IoU 가 낮은지를 라벨 좌표 전수로 확인했습니다.** 여덟 좌표로 배포되기에
  회전 박스라고 믿었는데 **13,069개 전부가 축 정렬**이었습니다. 장변 각도가
  0~10도에 6,343개, 80~90도에 6,726개, 그 사이는 0개입니다. `degrees=0` 이라
  증강도 회전을 만들지 않아, 모델은 회전된 박스를 한 번도 본 적이 없습니다.
- **종횡비는 배의 모양이 아니라 주석 습관이었습니다.** 0.958 에서 0.493 으로
  크기에 따라 단조 감소하는데, 실제 선박 비율은 크기와 무관합니다. 작은 배를
  뭉툭하게 칠한 것입니다. 3–5 px 구간의 폭 중앙값 3.61 px 는 36 m 인데, 길이
  40 m 급 배의 폭이 36 m 일 수 없습니다.
- **그래서 규약을 정하는 문제가 아니라 잴 대상이 없습니다.** 실제 선박이 가질 수
  있는 종횡비 전 범위(0.12~0.25)를 넣어도 폭이 **72~95% 가 2 px 미만**입니다.
  회전 박스의 단변은 어떤 규약에서도 허구이고, 측정 가능한 것은 중심점·길이·
  방향 셋뿐입니다. 더 정밀한 정답을 구해도 10 m 로 내리면 다시 서브픽셀입니다.
- **임계값만 올려 오탐을 97% 줄였습니다.** 재학습도 손실함수 수정도 없이
  운용점만 바꿔서입니다. 해역마다 최적 임계값이 달라(val 0.60, test 0.35)
  항만별로 따로 잡아야 한다는 것도 측정으로 확인했습니다.
- **창이 잘리며 라벨이 190 px 밀리는 버그를 찾았습니다.** `rasterio` 는 창이
  래스터 밖으로 나가면 말없이 잘라 주는데 `window_transform()` 은 요청한 창
  기준이라, 자른 만큼 라벨이 통째로 밀립니다. 에러도 경고도 없습니다.
  `w.crop()` 으로 먼저 자르니 정렬이 **99.5%** 로 회복됐습니다.
- **CPU 만으로 항만 한 곳을 1.61 초에 훑습니다.** 한 프로세스에서 PyTorch 와
  ONNX Runtime 을 함께 재니 같은 스크립트가 5 배 다른 값을 냈습니다. 두 런타임이
  스레드를 두고 경합한 계통 오차였고, 설정마다 프로세스를 새로 띄우니 반복 간
  차이가 1.0배로 내려왔습니다. 순수 순전파는 25.9 ms 이고 나머지 28 ms 는
  전처리·NMS·파이썬 오버헤드입니다.
- **남은 것 — 한국 확장은 4차에서 접었습니다.** 항만 22곳을 등록해 두었고 장면
  검색부터 탐지까지 한 함수로 돌아갑니다. 다만 국내 항만의 참조 자료는 GFW·AIS
  대조뿐이라 사람이 그린 정답이 없고, 정답이 없으면 정밀도를 잴 수 없습니다.
  그래서 4차는 실측 라벨이 공개된 **미국 군항 5곳**(HRSC2016)으로 갔습니다.
  한국 해역 데이터 보강과 탁수 대응 NIR(B08) 은 정답을 확보한 뒤의 일입니다.

## [4차] 미국 항만 5곳 선박탐지 웹앱 → [`04_ship_detection_real_labels/`](04_ship_detection_real_labels/)

3차의 월드모델(부산항, 정답 없음) 접근을 접고, **사람이 판독한 실측 라벨이
공개된 항만**으로 다시 짰습니다. 정답이 없으면 정밀도를 잴 수 없다는
전제입니다. 자료는 HRSC2016(Google Earth 약 0.45 m) — 미국 해군기지 5곳
1,059장 · 선박 2,964척 · 사람이 그린 회전상자입니다.

- **항만을 좌표로 식별했습니다.** 공식 문서는 "six famous harbors" 라고만
  하고 이름을 안 밝힙니다. XML 의 `Img_Location` 을 군집화하니 정확히 6곳이
  나왔고, 경도 부호가 빠져 있어 동경으로 읽으면 중국 내륙이 되는 것을
  서경으로 보정하니 **샌디에이고·노퍽·메이포트·에버렛·뉴포트** 가 실제
  기지와 2 km 안에서 맞았습니다. 지형으로 육안 확인했습니다.
- **XML 의 GSD(1.07 m)는 틀린 값입니다.** 그대로 믿으면 배 길이 중앙값이
  360 m 가 됩니다. 타일 레벨과 위도로 계산한 약 0.45 m 를 쓰면 선박 2,964척
  길이분포의 p99(347 m)가 Nimitz 급 항모(333 m)와 4 % 안에서 맞습니다.
- **YOLO11m-OBB, test 451장에서 F1 0.936 · AP50 0.970 · AP50-95 0.770.**
  학습 시드 3개 평균이고 항만별 AP50 은 0.94~0.99 입니다. 군함은 부두에
  비스듬히 대므로 축정렬 상자 대신 회전상자를 냅니다 — 길이·폭·방향이 나옵니다.
- 웹앱(항만 5곳을 돌아가며 test 영상에 탐지), 실행 파일, 단위 시험 포함.
  실행 파일(exe, 391 MB zip): https://drive.google.com/file/d/1_UyBzz7vqwi1Rt795klzWUuBGtC9tKXH/view?usp=sharing

리뷰 전 코드가 기준 브랜치를 오염시키지 않게 하고, PR 단위로 변경 이력을
추적하기 위해서입니다. 리뷰에서 지적이 나오면 새 브랜치를 파지 않고 열려 있는
PR 위에 반영 커밋을 올려, 지적과 대응이 같은 PR 안에 남게 합니다.
